# 每日短信巡检工具（patrol24）

2026-10-10 起，段枝宏要求每天纽约时间 9 点（David）和 21 点（曾翔宇）各在群里发一次巡检，文字描述，格式：

> 最近24小时内 1. 短信请求总量 2. 短信请求pass量 3. 非美国区号且非中国区号的 短信pass量 4. 区号在（21 个区号）范围内的短信pass量

这里的工具只在能连风控库的环境（MySQL 环境）里跑，桌面没有数据库连接。桌面上只做离线测试。

## 口径（定下来就不随手改）

| 项 | 定义 | 说明 |
|---|---|---|
| ① 短信请求总量 | `scene_id='LKUS_push'` 且 `$.para.email` 为空的请求数 | 和 Doris `l2_scene='1001'` 是同一口径：纽约日 09-20～09-26 七天逐日逐格相同（第三个包，探索 08） |
| ② 短信请求pass量 | ① 里 `result='PASS'` 的请求数 | `result` 是最终返回给调用方的结果；H5 上引擎判 REVIEW、最终返回 PASS 的也算在这里 |
| ③ 非美国区号且非中国区号的短信pass量 | ② 里区号是 1～4 位数字、且不是 1 和 86 的 | 区号为空、格式不对的不算进 ③，单独列在附加行；+852、+853、+886 算在 ③ 里；+1 包括加拿大等同区号的号码 |
| ④ 21 个区号的短信pass量 | ② 里区号在 `codes_21.txt` 里的 | 21 个区号照抄段枝宏的格式，和 strategy_eoHQ6QsOFRqp 的区号列表相同 |

- **窗口**：截止时间 T = 当天纽约时间 21:00（`--at 09:00` 就是 9 点那次），转成 UTC 写死；起点 = T 往前整 24 小时。
- **夏令时**：2026-11-01 这天也是整 24 小时，所以那天的起点显示成 10/31 22:00；2027-03-14 起点显示成 3/13 20:00。
- **区号写法**：库里区号带 '+'，比较时去掉 '+'；不带 '+' 的条数单独计数，作为检查项。
- **默认截止时间**：不带 `--date` 时，取"已经过了 2 分钟的最近一次截止时间"，所以过了午夜补跑取的是前一晚 21:00。
- **太早跑**：不带 `--date`、离今天的截止时间还有 12 小时以内（比如晚上 19:00～21:01）时，退出码 2，提示几点以后再跑，不出数。不会悄悄给出前一晚的数；要补前一晚，显式加 `--date`。

## 两条路

| 路 | 什么时候用 | 怎么做 |
|---|---|---|
| B（默认） | 一直可用，不需要网关地址 | `patrol24.py emit` 写出语句文件 → Claude 用 mcp-db-gateway 的查询工具逐条发送，每条回复原样存成同名 `.json` → `patrol24.py gate` 看负载和执行计划 → `patrol24.py collect` 核对并打印群消息 |
| A | 只在用户自己已经在当前 shell 里 export 了 `MCP_DB_GATEWAY_SSE` 时 | `patrol24.py run`，同一批语句文件经 `shard_runner.py` 的网关客户端发送；从不去 MCP 配置里找地址（2026-10-10 用户决定） |

每条语句都过 `shard_runner.guard()`：只读、优化器超时提示紧跟第一个 SELECT、每条最多 16 个分表、时间条件是写死的 UTC 字面量且不超过 24 小时，结果只有一行（按区号的那组每个区号一行）。

## 每晚（路 B）

1. `python3 toolkit/patrol24.py emit --per-code`。另一个查库任务像是在跑时，会退出码 3 并说明依据；用户确认后加 `--m1-active-ok`（2026-10-10 用户批准的例外：只发几条短语句，而且先过负载检查）。
2. 依次发送 `s0a`、`s0b`、`s0c`、`s0d`，然后跑 `patrol24.py gate <目录>`：GO 才继续；WAIT 就 20 分钟后重新 emit。
3. 依次发送 `w01_s1`…`w01_s4`，再发 `w01_c1`…`w01_c4`（按区号，附加行用）。
4. `python3 toolkit/patrol24.py collect <目录>`：核对过了才打印"复制下面这段发群"。

## 核对怎么防抄错（路 B 的回复是 Claude 抄存的）

- **语句身份**：每条回复带窗口起止和分表范围，和 manifest 对不上就停。
- **分表**：每条回复带"有数据的分表数"和"分表编号之和"。少了分表（正常每个分表每天几十条短信请求）就停；编号对不上也停。
- **重复读**：`dup_rows` = 行数 − 按（id, 时间, 区号）去重后的行数，必须是 0；某段把同一张表读了两遍会露出来。
- **时间**：回复里最早、最晚一行的时间必须落在窗口里，时间边界抄宽了会露出来。
- **数字**：
  - 总量 = 邮件行 + 短信行；短信 = PASS + REJECT + REVIEW + 其他结果；
  - pass = +1 + +86 + 空 + 无效 + ③；③ = ④ + 21 个以外；
  - 0 ≤ ④ ≤ ③ ≤ ② ≤ ①。
- **按区号的四条（`w01_c*`）**：加起来必须等于 ③、④、空、无效，这是对 ③、④ 的第二次独立测量。缺一条或对不上都停。
- 任何一项不过，退出码 4，不出群消息，也不写历史。

## 已知问题

- 旧的 `patrol.py --day 2026-11-01` 会被守卫拒绝：那个纽约日是 25 小时，超过单条语句 24 小时的上限。patrol24 用整 24 小时窗口，不受影响；按纽约日核对时 11-01 要拆成两段。
- 给 David 的 Doris 写法（`patrol24.py doris-sql --at 09:00 --date <日期>`）没在 Doris 上执行过。它用 `CONVERT_TZ` 按纽约时间截止，每天只改日期，夏令时自动处理。另外，源库这边第 3 项去掉了格式不对的区号，Doris 写法没有，`cc_odd_rows` 不为 0 时两边第 3 项会差这些条。
