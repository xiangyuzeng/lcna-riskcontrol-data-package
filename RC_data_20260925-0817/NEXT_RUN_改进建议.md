# NEXT_RUN 改进建议（对下一轮提示词的具体修改）

> 2026-09-25 本轮执行后整理。只提修改建议，不改提示词文件本身。

## 1. 范围与规则

1. **把 upush 的按日汇总表纳入允许范围**：`aws-luckyus-upush-rw` / `luckyus_iupushsms.t_verifycode_filled_statistics`（按日 × 来源项目 × 提供商 × 区号的发送数/填充数，无个人信息）。有了它，DR-007 可以答完，"准确率/误伤"也能用 OTP 回填做硬标签。建议 §3"Scope"加一条白名单：只读这张表的聚合。
2. **Redis**：如果希望记录风控 Redis（`luckyus-iriskcontrol`）的规模，请在 §3 明确允许 `INFO keyspace` / `DBSIZE`，并禁止 `SCAN`/`KEYS`（键名可能含手机号）。本轮按字面规则没有查询。
3. **行级抽取与行样本分开写时间上限**：§3 的"row samples ≤1 hour（主库）"本轮也用在了行级抽取（`_local_only`），建议写明"行级抽取每条语句 ≤1 小时，可多条覆盖整个窗口"。
4. **执行时限提示**：主库上建议直接写 `MAX_EXECUTION_TIME(10000)`（本轮用 10 s；提示词示例 60 s 在主库上偏宽）。
5. **明确脚本取数通道**：本轮 `MCP_DB_GATEWAY_SSE` 未设置，经用户同意改为运行时从本机 MCP 配置注入。下一轮可在提示词里直接说明允许这样做（地址只进子进程环境，不打印、不落盘）。

## 2. 背景事实（§2）需要更新

- 推送场景请求参数：实际只有 13 个必有键 + `recaptchaV3*`/`reviewRepeat`/`app`/`userNo`/`email`；`accessTime`、`phoneNoHead7`、`phoneNoMd5`、`uuidKey`、设备号只存在于参数配置表，请求里不出现。
- 带条件的累计特征：本轮证明过滤是生效的（DR-003）；请把"不要相信它们的值"改为"注意 `PARAMS_ERROR`/`DIMENSION_EMPTY` 表示没有值，引用它的策略会长期 0 命中"。
- featureDetail 平均约 12 KB/行（不是 20 KB）。
- V3 分数不能只按 `feature_TLXI8MNiNglz` 取：要按形状取（任一 reCAPTCHA 特征 apiResp 里的 `riskAnalysis.score`）。
- 分片键已知：`sharding_key = CONCAT(country_code, phone)`，DR-014 可以从待办里去掉，改为"每轮抽查一天是否仍成立"。
- cid 702 已知是 `SELF_SERVICE_MACHINE_US`（`request.$.cidOriginEnum` 可直接给出渠道），DR-006 可结案。
- 引擎按优先级执行、PASS 命中即停：DR-001 的问法应改成"请开发说明短路规则"，而不是在日志里找同时命中的样本。

## 3. 工作计划（§5）建议

1. P1 增加一步"全量服务器名字扫描"（本轮 64 个 MySQL + 1 个 PG，约 35 s），用于回答"数据还在哪"。
2. P2 增加"配置操作日志 `t_operation_log` 的逐条前后值（白名单字段）"，它是改名、改条件、改优先级的直接证据。
3. P3 建议先做一次行级抽取（只含标量与加盐哈希、只存本机），所有画像在本地算，再用纯 SQL 聚合核对表头数字。本轮核对 0 不一致，DB 负载也最低。
4. P5 的"去重用户"模板必须输出**窗口级**去重，禁止跨分组相加（本轮 tk01 第一版在 09-24 把 1,845 算成 1,982，已修）。
5. DR-003 的方法可以固定下来：先用同维度同窗口的无条件特征校准重算口径，再比"过滤前 / 过滤后"重算，再看逐日长序列。
6. 给 DR-010 写明攻击日判定规则的参数（本轮：前 28 天基线、中位数 + k×MAD、k=5），并要求用已知攻击起点只做检验。
