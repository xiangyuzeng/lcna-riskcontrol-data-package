# 05 取数手册与常见坑

> 2026-09-25 编写，依据本包的实测。对象：`aws-luckyus-iriskcontrolservice-rw` / `luckyus_iriskcontrolservice.t_access_log_0000…0063`（LKUS_push 为主）。
> 工具与模板见 `toolkit/README.md`；字段见 `dictionary/t_access_log_0000.md`。

## 1. 基本口径

| 项 | 口径 | 依据 |
|---|---|---|
| 时间 | `create_time` 是 UTC；纽约日边界用 `toolkit/ny_day_bounds.py` 算，窗口内不能跨夏令时切换（下一次 2026-11-01） | `results/p1_freshness.csv`、`results/p0_server_vars.csv` |
| 时间谓词 | 永远写 `create_time >= 'UTC' AND create_time < 'UTC'`，不要在 WHERE 里给 `create_time` 套函数；走索引 `idx_create_time_sharding_key` | `results/explain/` |
| 最终结果 | `result` 列 = `response.$.result`（返回调用方的结果）；引擎自己的结果在 `$.re.resultName`，两者约 0.2% 不同（DR-NEW-1） | `results/p1_result_sources_summary.csv` |
| 短信 / 邮件 | 源库没有 `l2_scene`；`$.para.email` 非空视为邮件候选，其余为短信（DR-002） | `results/p4_daily_series.csv` |
| 区号 | `country_code` 列与 `$.para.countryCode` 都带 `+`；统计时 `TRIM(LEADING '+' FROM x)` 后比较 | `results/p1_chk_consistency.csv` |
| IP 地理 | 基础列 `ip_city/ip_province/country/city` 全空；用 `$.para.realIpCountry/realIpProvince/realIpCity` | `results/p1_scene_rows.csv` |
| 去重手机号 | `sharding_key` = 带 `+` 的完整手机号；同一窗口内各分片 `COUNT(DISTINCT sharding_key)` 可相加 | DR-014 |
| V3 分数 | 按**形状**取：任一 reCAPTCHA 特征的 `comments.apiResp` 是含 `riskAnalysis.score` 的 JSON 对象 | DR-005 |
| cid | 105 Android / 106 iOS / 108 H5 / 702 自助机（`request.$.cidOriginEnum`） | DR-006 |

## 2. JSON 路径

| 需要的值 | 取法 |
|---|---|
| 请求参数对象 | `CAST(JSON_UNQUOTE(JSON_EXTRACT(request_strategy_engine, '$.para')) AS JSON)`（`$.para` 是**字符串**） |
| 在线 / 预上线命中数组 | `CAST(JSON_UNQUOTE(JSON_EXTRACT(response_strategy_engine, '$.re.hitStrategy')) AS JSON)`（同样是字符串）；`hitPreOnlineStrategy`、`hitBreakStrategy` 同理 |
| 命中元素字段 | `strategyId, strategyName, strategyType, status (ONLINE/PREONLINE), resultName, execPriority, vaild` |
| 特征数组 | `JSON_EXTRACT(response_strategy_engine, '$.re.featureDetail')`（原生数组）；元素 `featureId, name, type, code, result, comments.apiResp` |
| 规则数组 | `JSON_EXTRACT(response_strategy_engine, '$.re.ruleDetail')`（原生数组）；元素 `ruleId, name, type, code, result, comments` |
| 单个特征值 | `JSON_TABLE(JSON_EXTRACT(resp,'$.re.featureDetail'), '$[*]' COLUMNS (fid VARCHAR(64) PATH '$.featureId', code VARCHAR(64) PATH '$.code', v VARCHAR(64) PATH '$.comments.apiResp'))` + `WHERE fid = 'feature_…'` |
| 某策略是否命中 | `JSON_CONTAINS(<命中数组>, JSON_OBJECT('strategyId', 'strategy_…'))` |
| token 状态 | `JSON_EXTRACT(pa,'$.recaptchaV3Token') IS NULL` → 不存在；`= ''` → 为空；只取长度或状态，**不取值** |

## 3. 批量与速度（主库口径）

- 聚合语句：每条 ≤1 个纽约日、≤16 个分片（UNION ALL，每个分支各带时间谓词），带 `/*+ MAX_EXECUTION_TIME(10000) */`。行级抽取：每条 ≤1 小时，结果只留本机。
- 实测单条耗时（`results/timing.csv`，共 3,738 条分片语句）：16 分片中位数 0.54 s、95 分位 2.24 s、最长 5.96 s；最重的写法（全场景逐元素展开 featureDetail/ruleDetail）16 分片约 4.5 s，runner 会自动把批量减半。只看 LKUS_push、只取需要的标量时，16 分片 × 1 天约 0.5 s。
- 平均每行 LKUS_push：`response_strategy_engine` 27,304 B，其中 `featureDetail` 11,911 B、`ruleDetail` 13,852 B（`results/p1_payload_size.csv`）。**永远不要 SELECT 整个 JSON 列**。

## 4. 团队手册里的五个坑（仍然成立）

1. **不要 SELECT 整个 featureDetail / 任何整列 JSON**：在服务端用 `JSON_TABLE`/`JSON_EXTRACT` 只取标量。
2. **特征名会变，按 featureId 取**：本次还发现"按 featureId 也会漏"——同一个分数在不同日期挂在 `feature_MHv7nra5Z6T5` 或 `feature_TLXI8MNiNglz` 上，分数要按形状取（DR-005）。
3. **可能合并请求的 GROUP BY 要带每请求唯一键（`id`）**，或者用派生表先逐行计算、再聚合。
4. **网关拒绝含 `REPLACE(` 的 SELECT**：去 `+` 用 `TRIM(LEADING '+' FROM x)`。
5. **Doris `LATERAL VIEW` 是内连接**：featureDetail 为空的行会消失（本次 Doris 不可达，未复测）。

## 5. 本次新踩的坑

1. **`JSON_TABLE` 的第一个参数不能直接是派生表里的表达式列**（报 1210 Incorrect arguments）：包一层函数调用 `JSON_TABLE(JSON_EXTRACT(l.col, '$'), …)`。
2. **`JSON_TABLE(JSON_ARRAY(JSON_OBJECT(…), JSON_OBJECT(…)), '$[*]' … NESTED PATH …)` 会丢掉第二个元素的行**：在线与预上线命中要分两段 `JSON_TABLE` 再 UNION ALL。
3. **排序规则不一致**：`JSON_UNQUOTE(...)` 与表列直接比较报 1267 → 等值比较用 `CAST(a AS BINARY) = CAST(b AS BINARY)`；UNION 各分支同名列排序规则不同报 1271 → 统一 `CONVERT(x USING utf8mb4) COLLATE utf8mb4_0900_ai_ci`。
4. **`COUNT(DISTINCT)` 不能跨分组相加**：同一手机号同一天可能既 PASS 又 REJECT。按"区号 × 结果"分组后再相加，09-24 会把去重手机号从 1,845 算成 1,982。去重要在窗口级直接算（tk01/tk02 的 `window` 行）。
5. **uid 不是分片键**：7 日全部 LKUS_push 行里 9,069 个 uid 中 1,932 个跨分片，按分片相加会高估约一倍。
6. **`USER_PRIVILEGES` 会返回全实例账号的权限**（账号能读 `mysql.*` 时）：按 `CURRENT_USER()` 过滤，且不要取 `GRANTEE` 列。
7. **配置里的名称也可能带个人信息**：按手机号精确匹配的规则会把号码写进规则名与策略名，导出时名称列也要整值屏蔽。
8. **操作日志 `t_operation_log` 里的 `updateTime` 是 13 位毫秒时间戳**：用 `FROM_UNIXTIME(x/1000)` 转成 UTC 时间再落盘。
9. **`CONDITION_MISS` 不等于没有值**：带条件的累计特征在当前请求不满足条件时返回 `COUNTER_FEATURE_CONDITION_MISS`，但仍返回计数，规则照常使用（DR-003）。`PARAMS_ERROR`/`DIMENSION_EMPTY` 才是真的没有值——引用它的策略会长期 0 命中，看起来像"没流量"。
10. **时刻类规则按 UTC 比较**：配置里的 `02:00`、`01:10` 都是 UTC（DR-008）。
11. **优先级高的 PASS 命中后引擎不再执行其它策略**：统计"同时命中"时，PASS 与更低优先级的 REJECT 不会同时出现（DR-001）。

## 6. 取数前检查清单

- 时间窗口换算成 UTC 了吗？跨夏令时了吗？
- 是否只取需要的 JSON 标量？有没有任何个人信息字段（手机号、邮箱、uid、userNo、IP、设备号、token）的值被 SELECT？
- 语句过了 `shard_runner.py check` 吗？（单条语句、带执行时限提示、时间谓词是原列 + 字面量）
- 先在 0000 分片 EXPLAIN 一次，是 `range` 吗？
- 去重是窗口级算的吗？有没有跨分组 / 跨窗口相加？
- 分数、特征是按形状 / featureId 取的吗，有没有按名称？
