## 1. 输入与流程

1. **内联输入可行，建议保留「本轮覆盖项」写法。** 这次开头的覆盖项（新包、DR 清单、DR-027 自己的窗口、Doris 依赖写法、跳过 DR-028、交接方式）把歧义都消掉了，计划阶段不必问人。建议以后每轮都在提示词开头写同样一段，并把 DR 清单写成「运行 / 常设 / 短节 / 跳过」四类。
2. **交接仓库的可见性与 P7 第 7 步不一致。** 提示词要求交接仓库是 private，但 `lcna-riskcontrol-data-package` 是 public，所以本轮按覆盖项跳过第 7 步（没有 git 操作），zip 与 `.sha256` 留在运行目录。建议提示词只保留一种做法：要么由用户把仓库改为 private 后恢复第 7 步，要么删掉第 7 步、固定为「留在运行目录，由用户手工放进桌面 `_inbox/`」。
3. **策略效果类问题要先写清策略的时间线。** DR-027 假设「改动前按预上线命中」可比，但 `strategy_43NaEzJmiQFk` 2026-09-22 15:32:11 UTC 才新建、15:32:17 UTC 转预上线，改前只有约 23 小时可比，而且后半段是高峰（`results/p2_oplog_timeline.csv`、`results/dr027_period_rates.csv`）。建议 DR 模板加一行「被问策略的新建 / 状态变更时刻（取操作日志）」，并要求按精确时段给每 24 小时速率、按时段两半分别给出。
4. **「是 A 还是 B」的问题要允许两者分不开。** DR-027 问「43Na 拦下的，还是攻击量本身下降」；数据显示与 43Na 预上线的约 23 小时相比，上线后减少的请求几乎都是 43Na 条件成立的那部分（`results/dr027_period_rates.csv`），两种解释在计数上不可分。建议提示词要求：拆分类结论必须给出基线敏感性（`results/dr027_baseline_sensitivity.csv`）与「按是否满足该策略条件」的请求拆分，并写明「计数分解，非因果」。
5. **问题里写的日期要留余量。** DR-027 问的是 09-24、09-25，但 09-26 的非 +1 放行同样处在低位（`results/dr027_daily_decomposition.csv`）；本轮按覆盖项把窗口延到最后一个完整纽约日，建议以后默认如此。

## 2. 规则与守卫

1. **新鲜度检查在清晨会被 EXPLAIN 闸门误拦。** `p1_freshness` 取「最近 1 小时」，纽约 06:2x 时 0000 分片这一小时没有行，EXPLAIN 返回 `No matching min/max row`（没有扫描任何行），闸门按「计划异常」拒绝，整条链停下；本轮把窗口放宽到最近约 7 个 UTC 小时后续跑（`RUN_LOG.md` P1 note）。建议：新鲜度改取最近 6 小时；闸门把 `No matching min/max row` 视为「空区间、0 行」放行。
2. **列别名守卫有效。** 保留字表实时取自 `information_schema.KEYWORDS`（RESERVED=1），另加内建函数名；本轮没有再出现 1064。建议写进提示词 §3，作为执行器的固定检查。
3. **只留合并结果。** 聚合运行默认不写每分片的小文件（`--parts` 才写）：包内文件数（不含 `_local_only/`）从上一包的 3,825 降到约 400，隐私扫描与 MANIFEST 都快得多。
4. **批量大小沿用即可。** 本包全部运行共 3,390 条分片语句（`results/timing.csv`），中位 0.38 s，最长 5.01 s，超过 3 s 的 20 条（执行器随即减半批量）；聚合每条 16 分片、跨月逐日序列 8 分片的起步值不用改。命中类模板（`p2_hits_7d`、tk02 / tk03）每次运行的首批 16 分片语句约 1/5 超过 3 s、随即自动降到 8 分片，加不加短信过滤都一样（`results/timing.csv`）；这类模板可直接从 8 分片起步。
5. **运行前设 `PYTHONDONTWRITEBYTECODE=1`。** 本轮 `__pycache__/*.pyc` 曾出现在包里（其中记着本机绝对路径）；打包脚本会排除它们，但复制整个文件夹时会带走。`sql/local/p6_checks.py` 已加检查。

## 3. 方法

1. **tk10（唯一 REJECT 计数）建议列入 §6 的固定模板。** 「某策略上线拦下了多少本会放行的请求」这类问题，用 tk10 按纽约日 × 区号组 × 阶段 × 最终结果计数，再用 E1 逐格复核（本轮 348 格不一致 0，`results/dr027_crosscheck.csv`）。计数只给分解，不给因果；「若无该策略」一列是推算（假设请求量与其它策略判定不变；按请求次数计，被拒号码的重试会使它偏高，攻击方若因该策略减少请求又会使它偏低）。
2. **每个模板都要有短信口径参数。** P5 要求所有模板用短信规则，本轮复核时发现 tk02 / tk03 没有、tk06 抽取没有标记；已加 `sms_only`（tk02 / tk03）与 `email_nonempty`（tk06），两种口径都重测一致（`results/toolkit_tests/_test_summary.csv`）。建议提示词 §6 的模板清单写明「每个模板都有 `sms_only` 或等价列」。
3. **PASS 类预上线策略的额外召回口径写进 P3。** PASS 类策略上线后改变的是最终**不是** PASS 的命中；`toolkit/tk03_extra_recall.sql` 的 `pass_class` 参数已按此实现。
4. **一个指标一个值：注册表建议写进 P6。** `sql/local/metrics.py` 从 `results/` 只算一次主要数字（含窗口与口径），各页生成器都从这里取；`sql/local/p6_checks.py` 按带标签模式的指标扫描所有页面，出现不同的值就失败（`results/p6_metric_registry.csv`）。同一指标在两种口径下有两个值时（例：`strategy_GbsajBR69can` 短信口径与全部行），两个值都要登记、页面上都要标口径。
5. **一次行级抽取服务两个窗口。** E1 覆盖纽约日 09-19…09-26，同时供 P3 的 7 日窗口与 DR-027 的 8 日窗口使用，不必对同一批行解析两次 JSON。
6. **DR-003 常设项只看「是否恢复 SUCCESS」**，直接用 E1 里的计数器返回码，不必每轮重跑 32 天序列。
