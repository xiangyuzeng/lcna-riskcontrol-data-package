## 2. 规则与守卫

1. **MySQL 保留字当列别名会直接报 1064**：本轮 `DATE(create_time) AS utc_date` 失败（`UTC_DATE` 是函数名）。建议守卫增加「别名不能是 MySQL 保留字 / 内建函数名」的检查（`utc_date`、`current_date`、`rank`、`row_number` 等）；执行器已经在 EXPLAIN 阶段就失败、没有产生半截结果，失败的语句修正别名后重跑。
2. **逐行 CAST `$.para` 的聚合比预期重**：DR-024（31 天）与 DR-007（33 天）每条 16 分片语句 >3 s，执行器把批量降到 4，各花 10+ 分钟。建议：跨月的逐日聚合先按 8 分片起步；或者把 31 天的逐日聚合并入一次行级抽取（与 E1 同一抽取、在本地算），避免对同一批行解析两次 JSON。
3. **包体积**：执行器为每个分片写一个 `results/<name>/<shard>.csv`，本包因此有上千个小文件（隐私扫描和 MANIFEST 都要逐个处理）。建议聚合类运行加 `--no-parts` 选项，只保留合并后的 `results/<name>.csv`。

## 4. 工作计划（§5）建议

1. **DR-007 的读法写进提示词**：统计表按 `statistic_date`（UTC 日）汇总，只能与风控日志按 UTC 日关联；「发送数 / 风控放行」比值本身是统计表完整度的读数，比值明显下降的日子不能算回填率。区号级回填率只能做「折算」，要标明假设。
2. **P2 的名单计数**：名单表没有场景列；「按场景」要经名单特征（`namelist_type` × `check_type` × 接入方）映射，本轮已写成 `sql/local/p2_list_by_scene.py`，建议写进 P2 步骤。
3. **P3 的判断「是否带条件」**：累计特征配置里 `conditions: [""]` 是界面的空占位，不是条件；判断要看 `hasCondition` 与非空条件字符串，并补上操作日志里曾经带过条件的特征（`sql/local/p3_params.py`）。
4. **工具包模板的短信口径**：本轮把 tk01/04/05/07 的 `email_key` 从「email 键存在」改为「email 非空」，与提示词的短信定义一致（本窗口两者行数相同）。
